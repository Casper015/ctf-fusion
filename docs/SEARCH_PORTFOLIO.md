# Joint-action search experiment: action portfolio and per-branch ply-2 predictions

Task T0018. This is a code-only experiment on the trained models that already exist:
- no retraining, and no change to features, search depth, evaluation coefficients or V;
- V is off in every arm: the heuristic evaluation is the frozen baseline;
- it is kept apart from the V capacity experiment (T0016), so nothing under `training/` or `tests/` changed.

The production carriers (`c08_ponly.hpp`, `v12_ponly.hpp`) are untouched. Every change lives in the family carriers (`c08_ponly_f.hpp`, `v12_ponly_f.hpp`), generated by [`make_families.py`](../bots/p_only/tools/derive/make_families.py) with [`search_experiment.py`](../bots/p_only/tools/derive/search_experiment.py). Each change sits behind its own build setting, and all settings default to off. With every setting off, the family carriers reply exactly as the production carriers on the recorded 2- and 4-team games.

Nothing here is evidence of strength or timing. The host evaluation is a dependent task.

## 1. What already existed (verified on main, 1efe2c4 and later)

| Capability | Where | Status |
|---|---|---|
| Complete joint-movement enumeration (up to 5^3) for our three units, with an 8-mask DP allocating attacks against pickup utility | `ctfcombat::choose` in both carriers | kept |
| Asymmetric candidate expansion and sequential halving | C08 `asymmetricPlans`, `search::rank` | kept |
| An all-shooter volley alternative when a pickup is contested | v12 `choose`, `refine` | kept |
| Gated own-drop candidates | C08 `appendOwnDrops` | kept; it now also sees the portfolio's alternatives |
| A per-sample settlement and incoming-fire memo keyed by our joint movement | C08 `dynamics::ply1` | kept. It never hit before, since there was one plan per movement; with the portfolio it does (counted) |
| The checked lookahead predicts each branch from its own successor | C08 `refineChecked` | kept |
| Refinement predicts each candidate's own successor, per scenario | v12 `refine`: `fSession.branch(simState(two))`, parent = the root | verified, not changed |

The v12 check covers both requirements for a branch prediction:
- the successor state carries every unit's HP, deaths, carried flags, flag states and the settlement's attack events (`simState`);
- its parent is the real root (`PSession::branch`).

The P-only contract test checks both on recorded games (`branchParent`). No fix was needed.

None of these is presented as new.

## 2. What the audit found

1. **One action assignment per movement.** `choose` keeps a single DP-best assignment per movement triple. Alternate targets, attacking rather than picking up, and waiting rather than picking up never reach the search when they are not the analytic best for that movement.
2. **Movement-only equality in C08's checked lookahead.** It kept beam entries only `if (c.moveIndex != fallback.moveIndex)`, so an order with the incumbent's movement and other actions was dropped. C08's `addUniqueCandidate` and the deepen plan set already compare complete orders.
3. **v12 serialization.** Every negative target of an unladen unit was written as `P` (pickup), so an explicit wait would have become a pickup; an own drop had no `X`. The defaults never produce these codes, so play was unaffected. `ponlyActionText` now writes -1 as `-`, -2 as `P` (a carrier: `-`) and -3 as `X` (an unladen unit: `-`).
4. **C08 rollout semantics.** The sampled rollout credited a pickup to any unladen unit with a negative target. Only a pickup order (-2) picks up in the engine (`stepExact` agrees). Defaults are unaffected.
5. **Shared ply-2 predictions in C08's sampled search.** Per joint sample, the rivals' ply-2 orders come from the successor the *reference* plan reaches (the best plan so far), and every plan of the sample shares them. At the first, simultaneous turn this is correct: the enemies' orders are drawn from the observed root and cannot depend on our unrevealed order. At ply 2 the predicted states differ per plan: HP, deaths, pickups, attack events and our positions.
6. **Settlement order holds.** Moves, then attacks from post-move cells, then deaths, then pickups, then drops, then captures:
   - a carrier cannot fire, even one that drops this turn: the volley, `stepExact` and v12's `simStep` all read the pre-drop flag state;
   - a unit respawning this settlement can neither fire nor be hit.
7. **Branch data.** Since 7964c60, `training.branch_collect` skips a match whose carrier binary differs without saying so. That mixes "another arm" and "the carrier was rebuilt". The new tool tells them apart (section 5); `branch_collect` itself is unchanged, because T0016 holds `training/`.

## 3. Settings (all off by default)

| Setting | Effect |
|---|---|
| `PONLY_PORTFOLIO_K` (0; experiment 3) | For a shortlist of joint movements, up to K complete action assignments each, from a k-best version of the carrier's own 8-mask DP. Details below. |
| `PONLY_PORTFOLIO_MOVES` (3) | The shortlist: the incumbent's movement, then the best other movements by analytic value. |
| `PONLY_PLY2_MODE` (0) | C08 sampled search. **0:** the reference plan's prediction per sample, as now. **1:** each plan's prediction from its own settled successor. **2:** a diagnostic that plays as 0 and also scores every plan with its own prediction (section 6). |
| `PONLY_PLY2_CACHE` (1), `PONLY_PLY2_CACHE_SIZE` (64) | In modes 1 and 2, P views of identical successor states are built once per search call. |
| `PONLY_TURN_MS` (35), `PONLY_REFINE_MS` (24) | C08's turn deadline and v12's refinement deadline. Tests shrink them; deployment keeps them. |

**What the portfolio adds.** `choosePortfolio` is generated from each carrier's `choose()` text, restricted to the shortlist, and adds:
- alternate target allocations;
- attack against pickup;
- an explicit wait wherever a pickup is possible.

A subset of shooters in which one shooter adds nothing to the target's utility is skipped, so there is no unintended overkill. A target that needs three hits still gets the coordinated three-shot volley, because the third shot adds the kill.

**Where the alternatives go:**
- **C08 sampled search:** they join the asymmetric plan set after it is chosen, so they never displace a base plan.
- **C08 checked lookahead:** candidates are deduplicated by complete order, and up to K - 1 alternatives of the incumbent's movement are added.
- **v12:** alternatives follow the base refinement candidates; duplicates of beam entries are dropped.
- **Drops:** C08's existing gate (`appendOwnDrops`) applies to the extended set. v12 gets no drop alternatives: its evaluation has no possession-loss accounting.
- **Deadlines:** C08's lookahead returns the best order compared so far. A v12 deadline inside the alternatives keeps the best compared so far, since every base candidate has been compared; earlier, it returns the analytic fallback as before.

The portfolio runs only for the real turn's decision, never inside the lookahead's follow-up plans.

## 4. Caches and their contracts

| Work | Key | Notes |
|---|---|---|
| **Settlement and incoming fire** (existing memo) | Joint movement within one joint sample (the scenario) | Attack targets, pickups and drops cannot change movement settlement or the enemy fire that lands on our settled cells, so same-movement alternatives reuse it. Each plan's own volley, pickups and drops are applied afterwards. Counted: `memo_hits`, `memo_misses`. |
| **P views of ply-2 successors** (new) | Every field of the public state: turn, scores, each unit's cell, HP, carried flag and respawn time, every flag's status, cell, holder and timer, and the last attacks | Within one search call the parent (the real root), the perspective, the policy family and the model are fixed. The cache is cleared when the next call sets its root, and view buffers are reused. A state that differs only where P reads nothing (a dropped flag's return time) is still a separate entry: conservative, never merged. Counted: calls, hits, views built. Joint draws stay per sample on each branch's own distribution: aligned random numbers, `uniform(turn, team, sample, 29)` as before. |
| **V** | none | Not exercised: V is off in every arm. |

The real root's P view and history are never written by a branch:
- every branch view is built in the cache or scratch views, with the root as parent;
- the replay test prints the root predictions' digest every turn, and it is identical in every mode, branch order and branch count.

## 5. Branch-data candidates

[`bots/p_only/tools/branch_portfolio.py`](../bots/p_only/tools/branch_portfolio.py) reuses `training.branch_collect`'s exact root reproduction and branch play.

**Match selection.** Only matches of the declared arm are used, selected by the screen's match-name key:
- other arms' matches (and A/A copies) are skipped and counted;
- a selected match whose carrier binary differs from the manifest stops the run with the match id.

**Candidates.** Bounded, deduplicated by complete order, each labelled with its source:

| Source | What it is |
|---|---|
| recorded | the carrier's own order |
| `arm:<name>` | another variant's reply at the same root: it replays the same recorded inputs |
| move1 | one unit moves differently |
| move2 | two units move differently together |
| target | an alternate attack target |
| pickup_wait | pickup and wait swapped |
| drop | a carrier drops |
| transport | a carrier steps differently |

The sources take turns, so a small budget still covers every kind. Every candidate is decoded by the engine before it is played.

**Summary.** `summary.json` counts matches seen, selected and skipped; roots played and dropped; candidates by source; prefix mismatches (nondeterminism); faults; repeats; and resolved and unresolved pairs.

**Regret comparison.** [`branch_regret.py`](../bots/p_only/tools/branch_regret.py) reports, against the incumbent:
- outcome(compare arm's choice) − outcome(incumbent's choice);
- both regrets against the best candidate;
- both mean ranks.

All with map-clustered 95% intervals.

This prepares richer ranking data. It does not claim that the existing V learns from it without new training.

## 6. Verified here (development machine; fixed-work replays, no timing, not evidence)

`bots/p_only/tests/test_search_portfolio.py`, `test_branch_portfolio.py`, `portfolio_test.cpp` and `ply2_cache_test.cpp` check:
- **Defaults:** the family carriers reply exactly as production on the recorded 2- and 4-team games. On the 15-team game v12's fixed 24 ms refinement deadline binds, so even the production carrier's replies depend on the machine's speed there.
- **Portfolio cases:**
  - one movement keeps several complete assignments;
  - a one-hit target never gets two shooters;
  - a full-health target gets the three-shot volley;
  - pickup and explicit wait both appear;
  - a carrier never fires.
- **Serialization:** every target code serializes to the intended engine request; an explicit wait is never a pickup.
- **Cache keys:**
  - identical states share an entry;
  - HP, death, carried flag, attack and score changes make new entries and reach the encoder;
  - a flag-timer change makes a new entry although P reads no timer.
- **Cache equality:** the cached and the uncached per-branch search reply identically.
- **Diagnostic mode** replies exactly like the current search.
- **Root invariance:**
  - the root predictions are identical in every mode, with K = 2 or 3 and 2 or 3 shortlisted movements;
  - the P-only contract test (root history, branch parents, coherent states, engine comparison) passes on the 4- and 15-team games with the portfolio and per-branch predictions on.
- **Deadlines:** a zero deadline in C08, a zero refinement deadline in v12, and a cut inside v12's alternatives all return valid orders.
- **Branch data:**
  - only the declared arm's matches are used, and a changed binary stops the run;
  - candidates are distinct, sourced and decodable;
  - the root match is unchanged after its branches are played.

### Observations from the recorded fixtures

C08 at 64 joint samples per call (16 in the tests), deadlines removed. These are search-internal quantities, not outcomes:

| | 4 teams | 15 teams |
|---|---:|---:|
| Rival ply-2 draws where a plan's own prediction differs from the shared one | 11.8% | 11.6% |
| Searches whose best plan changes over all plans after the first round | 30 of 399 | 52 of 399 |
| Searches whose best plan changes among the final survivors | 19 of 399 | 30 of 399 |

On the 4-team game, at fixed work:

| Arm | Replies different from arm A |
|---|---:|
| C08 B (portfolio) | 57 of 400 |
| C08 C (per-branch) | 22 of 400 |
| C08 D (both) | 72 of 400 |
| v12 B (portfolio) | 26 of 400 |

Per-branch mode makes about 9.5 times as many ply-2 predictions per search, with 15% of P views reused. What that costs in samples at equal time is exactly what the host screen measures.

## 7. Host evaluation (dependent task)

1. **Fixed-work diagnostics.** [`search_diag.py`](../bots/p_only/tools/search_diag.py) on recorded games of the screen: replies changed against A, root digest mismatches (must be 0), prediction work, cache and memo hits, the diagnostic's prediction and ranking differences.
2. **Equal full-turn-time games.** [`screen_search.json`](../bots/p_only/profiles/screen_search.json): C08 A/B/C/D and v12 A/B, A/A copies of both A arms, interleaved paired fixtures, the official 2 s / 50 ms limits, fresh tuning seed 20261220. It reports paired utility per team-count band with map-group intervals, the interaction D − C − B + A, faults, late replies, p99 and maximum replies, and the search counters (samples displaced, truncations, predictions, alternatives).
3. **Branch regret against the incumbent.** `branch_portfolio.py` with the A arm as incumbent and B (or D) as the compare arm, then `branch_regret.py`.

**Reading the results:**
- An interval that includes zero is "not shown".
- More candidates, changed decisions or higher internal search scores are not a strength result, and neither is one favourable run.
- The production default stays as it is unless an arm shows a useful improvement within the same whole-turn budget. Confirmation then needs an unseen seed (T0006).
